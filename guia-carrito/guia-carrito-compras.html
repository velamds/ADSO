Cómo construir un carrito de compras con localStorage y JavaScript

Paso a paso vamos a construir un catálogo de productos leído desde un archivo .json, una vista de detalle, un carrito persistente en el navegador con localStorage, un ícono con contador de artículos y un checkout — todo con Bootstrap 5.3 y JavaScript nativo, explicando qué hace cada función, por qué se usa y qué alternativas existen.

00 INTRODUCCIÓN

Qué vamos a construir y por qué en este orden

Un carrito de compras "solo front-end" (sin backend ni base de datos) tiene cuatro piezas que dependen unas de otras. Por eso la guía avanza en este orden: primero los datos (de dónde salen los productos), luego cómo se muestran, luego cómo se guardan las decisiones del usuario (localStorage) y por último cómo esas decisiones se reflejan en la interfaz (ícono, vista de carrito, checkout).

4. Interfaz

Por qué localStorage y no un backend
Para aprender el flujo completo de un carrito (agregar, quitar, persistir, mostrar totales) no necesitas un servidor. localStorage permite que el carrito sobreviva a recargar la página o cerrar la pestaña, que es la señal mínima de "carrito persistente" que un usuario espera. Cuando el proyecto necesite usuarios reales, inventario compartido o pagos, ese carrito se migra a un backend (ver paso 12).
01 DATOS

Los productos viven en un archivo products.json

En lugar de "quemar" los productos dentro del HTML o del JavaScript, los separamos en un archivo de datos. Cada producto es un objeto con, como mínimo, un id único, nombre, precio, stock y un imagen con la URL de su foto.

Por qué separar datos de la interfaz
Si mañana cambian los precios o llega un producto nuevo, alguien edita un archivo de datos —no busca etiquetas <div> repetidas en el HTML—. Esto también es lo que hace posible que, más adelante, ese mismo JSON pueda salir de una API real sin tocar el código que dibuja la interfaz.

Leer el JSON con fetch

app.js
async function cargarProductos() {
  const respuesta = await fetch('./products.json');   // 1. Pide el archivo
  if (!respuesta.ok) {                                  // 2. Verifica que llegó bien (status 200-299)
    throw new Error('No se pudo cargar el catálogo');
  }
  const productos = await respuesta.json();             // 3. Convierte el texto JSON en un array de objetos JS
  return productos;
}

fetch devuelve una Promise, por eso se usa await dentro de una función async: el navegador sigue respondiendo mientras espera la respuesta, en lugar de congelarse.

Antiejemplo: ignorar los errores
// ❌ Si el archivo no existe o el servidor responde 404,
// esto sigue intentando leer un JSON que no llegó y el error
// se ve como un fallo "misterioso" más adelante en el código.
fetch('./products.json')
  .then(r => r.json())
  .then(productos => pintarProductos(productos));
Falta comprobar respuesta.ok y falta un .catch() (o un try/catch) para mostrarle algo al usuario si la carga falla, en vez de dejar la pantalla en blanco.

Versión con manejo de errores (la que usa la demo de esta guía)

La función anterior es la idea central, pero deja el programa "roto" si fetch falla —por ejemplo, si abres el archivo con doble clic (file://) en vez de con un servidor—. Una versión más robusta atrapa el error y devuelve datos de respaldo en vez de dejar la página en blanco:

app.js
async function cargarProductos() {
  try {
    const respuesta = await fetch('./products.json');
    if (!respuesta.ok) throw new Error('respuesta no ok');
    return await respuesta.json();
  } catch (error) {
    console.warn('No se pudo leer products.json, se usa un respaldo local:', error);
    return PRODUCTOS_RESPALDO; // un arreglo con los mismos datos, copiado dentro del propio app.js
  }
}

Esta es la versión que usa la demo del paso 10 de esta guía. En un proyecto real, servido siempre por http, el catch casi nunca se activa; aquí lo agregamos para que puedas abrir el archivo final directamente y verlo funcionar sin montar un servidor.

Tener la función no sirve de nada si nunca se ejecuta. Se necesita: (1) una variable donde guardar el resultado, para poder usarlo desde cualquier otra función de la app, y (2) un punto de entrada que llame a cargarProductos() en cuanto la página cargue.

app.js
let catalogo = []; // aquí quedan los productos ya cargados, disponibles para TODA la app

async function iniciarApp() {
  catalogo = await cargarProductos();  // espera a que el fetch termine...
  console.log(catalogo);               // ...y de momento solo los mostramos en la consola
}

// Se llama iniciarApp() en cuanto el HTML terminó de cargar en el navegador
document.addEventListener('DOMContentLoaded', iniciarApp);
Por qué esperar a DOMContentLoaded
Este evento se dispara cuando el navegador terminó de leer todo el HTML (aunque las imágenes todavía estén cargando). Llamar a iniciarApp ahí garantiza que elementos como #grid-productos ya existan en el DOM antes de que el código intente usarlos — algo que en los próximos pasos sí nos hará falta, cuando iniciarApp empiece a pintar cosas en pantalla.
Forma de ejecutar el código de inicioCuándo se disparaUso típico
document.addEventListener('DOMContentLoaded', fn) HTML listo, sin esperar imágenes/CSS externo La usada aquí: es el momento correcto para buscar elementos por id
window.addEventListener('load', fn) Página completamente cargada, incluidas imágenes Cuando se necesita medir o depender de recursos externos ya cargados
Script simplemente al final del <body>, sin evento En cuanto el navegador llega a esa línea Funciona en la práctica porque el HTML ya se leyó completo antes de esa línea, pero es menos explícito sobre la intención

02 ESTRUCTURA

Bootstrap 5.3 y el esqueleto HTML

Bootstrap aporta la grilla, las tarjetas, el offcanvas del carrito y los modales del checkout, para no reinventar CSS de layout. Se agrega por CDN, que es la forma más rápida de empezar sin instalar nada.

index.html — <head>

  href="https://cdn.jsdelivr.net/npm/bootstrap@5.3.3/dist/css/bootstrap.min.css"
  rel="stylesheet">

<!-- al final del body, para que el DOM ya exista cuando se ejecute -->
<script
  src="https://cdn.jsdelivr.net/npm/bootstrap@5.3.3/dist/js/bootstrap.bundle.min.js">
</script>

CDN vs. instalación local (npm)

OpciónVentajaLimitaciónRecomendado para
CDN (<link> / <script>) Cero configuración, cachea entre sitios Depende de internet; sin control de versión exacto si no se fija Prototipos, guías, sitios estáticos simples

Por qué el JS de Bootstrap va antes de cerrar </body>
El HTML se procesa de arriba hacia abajo. Si el <script> se coloca en el <head>, el navegador intentaría ejecutar código que manipula elementos (como el offcanvas del carrito) antes de que esos elementos existan en el DOM.

El esqueleto: dos vistas que se muestran u ocultan

Usamos una sola página con dos contenedores: uno para el listado de productos y otro para el detalle de un producto. Solo uno de los dos es visible a la vez, usando el atributo HTML hidden. Más adelante (pasos 07 a 09) agregaremos el ícono del carrito, el panel lateral del carrito y el checkout — por ahora dejamos ese espacio reservado como comentario para no adelantar código que todavía no se explica.

Este es el <body> completo con el que vamos a trabajar desde aquí. Los id que ves (vista-listado, grid-productos, vista-detalle...) son los mismos que usaremos en todo el JavaScript de los siguientes pasos — cópialos tal cual.

Por qué hidden y no display:none en CSS
hidden es un atributo HTML estándar: cualquiera que lea el marcado entiende de inmediato que esa vista empieza oculta, sin tener que ir a buscar una regla CSS. Alternar visibilidad después es tan simple como elemento.hidden = true o elemento.hidden = false desde JavaScript — lo usaremos en el paso 04.

03 LISTADO

Pintar el listado de productos con JavaScript

Con los productos ya cargados (paso 01) dentro de una variable catalogo, se recorren y se genera una tarjeta Bootstrap por cada uno, insertándolas dentro de #grid-productos (el contenedor que dejamos listo en el paso 02).

app.js
let catalogo = []; // aquí guardaremos los productos ya cargados (paso 01)

function formatearPrecio(valor) {
  return valor.toLocaleString('es-CO', { style: 'currency', currency: 'COP', maximumFractionDigits: 0 });
}

function pintarProductos(productos) {
  const contenedor = document.getElementById('grid-productos');

  if (productos.length === 0) {
    contenedor.innerHTML = '<p class="text-muted">No hay productos para mostrar.</p>';
    return;
  }

  contenedor.innerHTML = productos.map(p => `
    <div class="col-md-4 col-sm-6">
      <div class="product-card" data-id="${p.id}">
        <img src="${p.imagen}" alt="${p.nombre}" class="img-abrir-detalle">
        <div class="p-3">
          <span class="badge text-bg-light border mb-1">${p.categoria}</span>
          <h3 class="h6 mb-1 nombre-abrir-detalle" role="button">${p.nombre}</h3>
          <p class="price mb-2">${formatearPrecio(p.precio)}</p>
          <button class="btn btn-dark btn-sm w-100 btn-agregar">Agregar</button>
        </div>
      </div>
    </div>
  `).join('');
}

Nota: catalogo y formatearPrecio se declaran una sola vez y se reutilizan en los pasos siguientes (detalle, carrito, checkout); no hace falta volver a escribirlos.

Por qué Array.prototype.map + join('')
map transforma cada producto en un trozo de HTML (string), y join('') los une en un solo string sin separadores. Es una forma declarativa de decir "por cada producto, esta plantilla", en lugar de ir concatenando HTML manualmente en un bucle.
Antiejemplo: interpolar datos sin control (XSS)
// ❌ Si "nombre" viniera de un usuario (no de tu propio JSON),
// esto ejecutaría cualquier <script> que contenga el texto.
contenedor.innerHTML += `<h3>${productoDelUsuario.nombre}</h3>`;
Para datos que tú controlas (tu propio products.json) esto es aceptable. Si el contenido viniera de un formulario o de otro usuario, se debe sanitizar o usar textContent en vez de innerHTML.

innerHTML vs. createElement vs. plantillas (<template>)

TécnicaLegibilidadSeguridadRendimiento
innerHTML + template literals Alta Requiere cuidado con XSS Bueno para listas medianas
document.createElement + appendChild Media (más líneas) Más seguro por defecto Mejor en listas muy grandes o que cambian mucho
Elemento <template> + cloneNode Media Seguro Muy bueno, reutiliza una estructura ya parseada
Un framework (React, Vue, Svelte…) Alta a gran escala Seguro por defecto (escapan variables) Óptimo con actualizaciones frecuentes de UI

Delegación de eventos: un solo listener para todas las tarjetas

Una tarjeta tiene dos acciones posibles: hacer clic en "Agregar" (lo resolvemos ya mismo, en el paso 06) o hacer clic en la imagen/nombre para abrir el detalle (la función mostrarDetalle la escribimos en el paso 04 — aquí solo dejamos lista la conexión).

app.js
// En vez de poner un listener por cada botón/tarjeta (que además se
// perdería cada vez que se vuelve a pintar el listado), se escucha
// el contenedor completo UNA sola vez y se revisa qué se hizo clic.
document.getElementById('grid-productos').addEventListener('click', (evento) => {
  const tarjeta = evento.target.closest('.product-card');
  if (!tarjeta) return;                     // el clic no fue dentro de ninguna tarjeta
  const id = tarjeta.dataset.id;

  if (evento.target.closest('.btn-agregar')) {
    agregarAlCarrito(id, 1);                // función del paso 06
    return;
  }
  if (evento.target.closest('.img-abrir-detalle') || evento.target.closest('.nombre-abrir-detalle')) {
    mostrarDetalle(id);                     // función del paso 04
  }
});
Por qué delegación y no un listener por botón
Cada vez que pintarProductos vuelve a ejecutarse (por ejemplo, al filtrar), los botones viejos se destruyen y se crean unos nuevos. Un listener puesto directamente sobre un botón desaparece con él. El contenedor padre, en cambio, no se vuelve a crear, así que su listener sigue funcionando para cualquier botón o tarjeta —incluso los nuevos— gracias al event bubbling (el clic "burbujea" desde el elemento exacto hasta sus contenedores).

Extra opcional: filtrar por categoría

No es indispensable para tener un carrito funcional, pero es una buena forma de practicar filter. Agrega este <select> justo encima de #grid-productos (dentro de #vista-listado):

index.html
<select class="form-select form-select-sm w-auto mb-3" id="filtroCategoria">
  <option value="">Todas las categorías</option>
</select>
app.js
function poblarFiltroCategorias() {
  const select = document.getElementById('filtroCategoria');
  const categorias = [...new Set(catalogo.map(p => p.categoria))]; // categorías sin repetir
  categorias.forEach(cat => {
    const opcion = document.createElement('option');
    opcion.value = cat;
    opcion.textContent = cat;
    select.appendChild(opcion);
  });
}

document.getElementById('filtroCategoria').addEventListener('change', (evento) => {
  const categoriaElegida = evento.target.value;
  const productosFiltrados = categoriaElegida
    ? catalogo.filter(p => p.categoria === categoriaElegida)
    : catalogo;
  pintarProductos(productosFiltrados);
});
Por qué new Set(...) para las categorías
Set es una colección que no admite valores repetidos. Convertir el arreglo de categorías en un Set y luego de vuelta en arreglo con [...set] es la forma más corta de "quitar duplicados" sin escribir un bucle manual con condicionales.

Completar iniciarApp() para que pinte el listado

En el paso 01 dejamos iniciarApp mostrando los productos solo en la consola, porque pintarProductos todavía no existía. Ahora que ya la escribimos, se actualiza esa misma función para que además dibuje las tarjetas y llene el filtro:

app.js
async function iniciarApp() {

  poblarFiltroCategorias();            // este paso

Esto reemplaza la versión de iniciarApp del paso 01 (la del console.log) — no se escriben las dos, solo queda esta versión más completa. El listener document.addEventListener('DOMContentLoaded', iniciarApp) ya estaba puesto desde el paso 01 y no cambia.

La función que rellena esos campos

app.js
let productoActual = null; // el producto que se está mostrando en el detalle

function mostrarDetalle(idProducto) {
  productoActual = catalogo.find(p => p.id === idProducto);
  if (!productoActual) return;

  document.getElementById('detalle-imagen').src = productoActual.imagen;
  document.getElementById('detalle-categoria').textContent = productoActual.categoria;
  document.getElementById('detalle-nombre').textContent = productoActual.nombre;
  document.getElementById('detalle-descripcion').textContent = productoActual.descripcion;
  document.getElementById('detalle-precio').textContent = formatearPrecio(productoActual.precio);
  document.getElementById('detalle-stock').textContent = `${productoActual.stock} unidades disponibles`;
  document.getElementById('detalle-cantidad').value = 1; // reinicia la cantidad cada vez que se abre

  document.getElementById('vista-listado').hidden = true;
  document.getElementById('vista-detalle').hidden = false;
}

// Botón "Volver al catálogo"
document.getElementById('btnVolver').addEventListener('click', () => {
  document.getElementById('vista-detalle').hidden = true;
  document.getElementById('vista-listado').hidden = false;
});

// Botón "Agregar al carrito" DESDE el detalle (respeta la cantidad elegida)
document.getElementById('btnAgregarDetalle').addEventListener('click', () => {
  if (!productoActual) return;
  const cantidad = Math.max(1, parseInt(document.getElementById('detalle-cantidad').value, 10) || 1);
  agregarAlCarrito(productoActual.id, cantidad); // función del paso 06
});
Por qué Array.prototype.find
find recorre el arreglo y devuelve el primer elemento que cumple la condición (o undefined si ninguno la cumple). Es la herramienta correcta cuando se busca "el" elemento por un identificador único, a diferencia de filter, que devolvería un arreglo aunque solo exista una coincidencia.
Por qué Math.max(1, parseInt(...) || 1)
parseInt puede devolver NaN si el campo está vacío o tiene texto no numérico; || 1 cubre ese caso. Math.max(1, ...) evita que alguien escriba 0 o un número negativo en el campo de cantidad y rompa el cálculo del total más adelante.
Antiejemplo: buscar por posición en vez de por id
// ❌ Si el catálogo cambia de orden (filtros, ordenar por precio…)
// el índice ya no corresponde al mismo producto.
function mostrarDetalle(indice) {
  productoActual = catalogo[indice];
}
Usar el id del producto (y no su posición en el arreglo) evita este tipo de bug silencioso.

05 PERSISTENCIA

Fundamentos de localStorage

localStorage es un almacén clave-valor que el navegador guarda por origen (protocolo + dominio + puerto) y que persiste aunque se cierre la pestaña o el navegador. Solo guarda strings, así que los objetos/arreglos se convierten con JSON.stringify al guardar y con JSON.parse al leer.

consola del navegador
localStorage.setItem('color-favorito', 'azul');   // guardar un string
localStorage.getItem('color-favorito');           // → "azul"

const carrito = [{ id: 'p01', cantidad: 2 }];
localStorage.setItem('carrito', JSON.stringify(carrito)); // objeto → string
const leido = JSON.parse(localStorage.getItem('carrito')); // string → objeto

localStorage.removeItem('color-favorito');        // borrar una clave
localStorage.clear();                             // borrar todo lo del origen
Antiejemplo: guardar el objeto directamente
// ❌ localStorage convierte cualquier valor a string automáticamente,
// pero para un objeto lo convierte al texto inútil "[object Object]".
localStorage.setItem('carrito', carrito);
localStorage.getItem('carrito'); // → "[object Object]"  (se perdió la información)
Antiejemplo: leer sin comprobar que exista
// ❌ La primera vez que alguien visita el sitio, la clave "carrito"
// no existe todavía: getItem devuelve null, y JSON.parse(null) explota
// de forma silenciosa en algunos casos o devuelve null en otros.
const carrito = JSON.parse(localStorage.getItem('carrito'));
carrito.push(nuevoItem); // 💥 Error: Cannot read properties of null
// ✅ Siempre con un valor por defecto:
const carrito = JSON.parse(localStorage.getItem('carrito')) || [];

localStorage vs. otras formas de guardar datos en el navegador

MecanismoPersiste tras cerrar el navegadorCapacidad aprox.Se envía al servidorCuándo usarlo
localStorage Sí 5–10 MB No Preferencias, carrito, borradores — este proyecto
sessionStorage No (solo dura la pestaña) 5–10 MB No Datos temporales de un solo flujo (ej. pasos de un wizard)
Cookies Sí (configurable con expiración) ~4 KB Sí, en cada petición Sesiones de autenticación, datos que el servidor necesita leer
IndexedDB Sí Cientos de MB o más No Grandes volúmenes de datos, apps offline complejas
Por qué localStorage y no cookies para el carrito
Las cookies viajan en cada petición HTTP al servidor, lo cual es innecesario (y más lento) para datos que solo le importan al navegador. Además su límite de ~4KB se queda corto si el carrito crece. localStorage es más grande, no viaja por la red y es más simple de leer/escribir con JS.
06 MODELO DE DATOS

Cómo modelar el carrito

Dos formas de guardar el carrito en localStorage:

ModeloEjemploProblema / ventaja
❌ Guardar el producto completo 
[{ id:"p01", nombre:"Teclado...",
  precio:289000, imagen:"...", cantidad:2 }]
 Duplica datos que ya están en products.json. Si el precio cambia en el catálogo, el carrito queda con el precio viejo ("desincronizado").
✅ Guardar solo id + cantidad 
[{ id:"p01", cantidad:2 },
 { id:"p04", cantidad:1 }]
 El carrito es una lista mínima. Nombre, precio e imagen se buscan en el catálogo (find) cada vez que hay que mostrar el carrito, así siempre están al día.
carrito.js
const CLAVE_CARRITO = 'carrito';

function obtenerCarrito() {
  return JSON.parse(localStorage.getItem(CLAVE_CARRITO)) || [];
}

function guardarCarrito(carrito) {
  localStorage.setItem(CLAVE_CARRITO, JSON.stringify(carrito));
  document.dispatchEvent(new CustomEvent('carrito:actualizado', { detail: carrito }));
}

function agregarAlCarrito(idProducto, cantidad = 1) {
  const carrito = obtenerCarrito();
  const item = carrito.find(i => i.id === idProducto);

  if (item) {
    item.cantidad += cantidad;          // ya estaba: solo sube la cantidad
  } else {
    carrito.push({ id: idProducto, cantidad }); // no estaba: se agrega
  }
  guardarCarrito(carrito);
}

function quitarDelCarrito(idProducto) {
  const carrito = obtenerCarrito().filter(i => i.id !== idProducto);
  guardarCarrito(carrito);
}

function cambiarCantidad(idProducto, nuevaCantidad) {
  const carrito = obtenerCarrito();
  const item = carrito.find(i => i.id === idProducto);
  if (!item) return;

  if (nuevaCantidad <= 0) {
    return quitarDelCarrito(idProducto);
  }
  item.cantidad = nuevaCantidad;
  guardarCarrito(carrito);
}
Por qué centralizar todo en guardarCarrito()
Cada función que cambia el carrito (agregar, quitar, cambiar cantidad) termina llamando a la misma función guardarCarrito. Así hay un solo lugar responsable de escribir en localStorage y de avisar al resto de la interfaz que algo cambió, en vez de repetir localStorage.setItem(...) en cada función (y arriesgarse a olvidarlo en alguna).
Antiejemplo: permitir duplicados
// ❌ Sin buscar si el producto ya está, cada clic en "Agregar"
// crea una línea nueva en vez de sumar la cantidad.
function agregarAlCarrito(idProducto) {
  const carrito = obtenerCarrito();
  carrito.push({ id: idProducto, cantidad: 1 });
  guardarCarrito(carrito);
}
// Resultado: el mismo producto aparece 3 veces en el carrito
// en vez de una vez con cantidad 3.
07 INTERFAZ

Ícono del carrito con contador de artículos

El número sobre el ícono del carrito (el mismo que ves arriba, en la barra de esta guía) tiene que actualizarse cada vez que el carrito cambia, sin importar desde qué parte del código haya cambiado.

Estrategia para refrescar el contadorCómo funcionaCuándo conviene
Llamar a actualizarContador() manualmente al final de cada función del carrito Cada función (agregar, quitar…) invoca la actualización Proyectos pequeños; fácil de seguir pero fácil de olvidar una llamada
Evento personalizado (CustomEvent) guardarCarrito emite un evento; cualquier parte de la UI que necesite reaccionar se suscribe una vez La usada en esta guía: desacopla "qué cambió" de "quién debe reaccionar"
Evento nativo storage Se dispara solo cuando otra pestaña modifica el mismo localStorage Sincronizar el carrito entre varias pestañas abiertas del mismo sitio
Sondeo (setInterval revisando localStorage) Se revisa el valor cada cierto tiempo No recomendado: gasta recursos comprobando algo que ya se sabe cuándo cambia

El HTML del ícono

Agrega este botón donde quieras mostrar el carrito (por ejemplo, en una barra superior antes de #vista-listado). El número dentro del <span> es el que se va a actualizar con JavaScript — fíjate que usa la clase cart-badge, no un id: así el mismo contador puede repetirse en más de un lugar de la página (por ejemplo arriba y en un menú) y los dos se actualizan a la vez.

        data-bs-toggle="offcanvas" data-bs-target="#offcanvasCart">
  <i class="bi bi-cart3"></i> Carrito
  <span class="badge rounded-pill bg-dark cart-badge">0</span>

data-bs-toggle="offcanvas" y data-bs-target="#offcanvasCart" son atributos de Bootstrap: le dicen al botón que, al hacer clic, debe abrir el panel lateral con ese id —el que construimos en el paso 08—. No hace falta escribir JavaScript para eso, Bootstrap ya lo maneja.

El JavaScript que mantiene el número al día

app.js
function actualizarContador() {
  const carrito = obtenerCarrito();
  const totalArticulos = carrito.reduce((suma, item) => suma + item.cantidad, 0);

  document.querySelectorAll('.cart-badge').forEach(el => {
    el.textContent = totalArticulos;
  });
}

// Se suscribe UNA vez al evento personalizado emitido en guardarCarrito()
document.addEventListener('carrito:actualizado', actualizarContador);

// Y también al cargar la página, para reflejar lo que ya había en localStorage
document.addEventListener('DOMContentLoaded', actualizarContador);
Por qué reduce para el total y no la longitud del arreglo
carrito.length contaría "2 productos distintos" como 2, aunque uno tenga cantidad 5. reduce suma la propiedad cantidad de cada línea, dando el número real de artículos en el carrito (que es lo que el usuario espera ver en el ícono).
Checkpoint del paso 07
Agrega algún producto desde el listado o el detalle y el número del botón "Carrito" debe cambiar de 0 a la cantidad correspondiente, incluso si recargas la página (porque actualizarContador se ejecuta también en DOMContentLoaded, leyendo lo que ya había en localStorage).

Pintar las líneas del carrito

app.js
function pintarVistaCarrito() {
  const carrito = obtenerCarrito();
  const contenedor = document.getElementById('lineas-carrito');

  if (carrito.length === 0) {
    contenedor.innerHTML = '<p class="text-muted small">Tu carrito está vacío.</p>';
    document.getElementById('total-carrito').textContent = formatearPrecio(0);
    return;
  }

  contenedor.innerHTML = carrito.map(item => {
    const producto = catalogo.find(p => p.id === item.id);
    if (!producto) return '';                 // por si el producto ya no existe en el catálogo
    const subtotal = producto.precio * item.cantidad;
    return `
      <div class="d-flex gap-2 border-bottom py-2" data-id="${item.id}">
        <img src="${producto.imagen}" alt="" style="width:52px;height:52px;object-fit:cover;border-radius:8px">
        <div class="flex-grow-1">
          <div class="fw-semibold small">${producto.nombre}</div>
          <div class="text-muted small">${formatearPrecio(producto.precio)}</div>
          <div class="d-flex align-items-center gap-2 mt-1">
            <button class="btn btn-sm btn-outline-secondary py-0 px-2 btn-restar">−</button>
            <span class="small">${item.cantidad}</span>
            <button class="btn btn-sm btn-outline-secondary py-0 px-2 btn-sumar">+</button>
            <button class="btn btn-sm btn-link text-danger ms-auto btn-quitar">Quitar</button>
          </div>
        </div>
        <div class="fw-bold small">${formatearPrecio(subtotal)}</div>
      </div>`;
  }).join('');

  const total = carrito.reduce((suma, item) => {
    const producto = catalogo.find(p => p.id === item.id);
    return producto ? suma + producto.precio * item.cantidad : suma;
  }, 0);
  document.getElementById('total-carrito').textContent = formatearPrecio(total);
}

// Se repinta cada vez que el carrito cambia (mismo evento del paso 07)
document.addEventListener('carrito:actualizado', pintarVistaCarrito);
document.addEventListener('DOMContentLoaded', pintarVistaCarrito);

Botones +, − y "Quitar" dentro del carrito

Igual que en el paso 03, un solo listener sobre el contenedor #lineas-carrito maneja los tres botones de todas las líneas, aunque se vuelvan a pintar constantemente:

app.js
document.getElementById('lineas-carrito').addEventListener('click', (evento) => {
  const linea = evento.target.closest('[data-id]');
  if (!linea) return;
  const id = linea.dataset.id;
  const carrito = obtenerCarrito();
  const item = carrito.find(i => i.id === id);
  if (!item) return;

  if (evento.target.closest('.btn-sumar'))  cambiarCantidad(id, item.cantidad + 1); // paso 06
  if (evento.target.closest('.btn-restar')) cambiarCantidad(id, item.cantidad - 1); // paso 06
  if (evento.target.closest('.btn-quitar')) quitarDelCarrito(id);                   // paso 06
});
Por qué leer el id desde data-id
Cada línea del carrito lleva el atributo data-id="${item.id}" (ver el HTML generado arriba). evento.target.closest('[data-id]') sube desde el botón exacto que se clickeó hasta encontrar ese contenedor, y linea.dataset.id lee el atributo — así los tres botones de una misma línea siempre operan sobre el producto correcto, sin importar el orden en que se repinte la lista.

reduce vs. un bucle for para el total

EnfoqueCódigoCuándo preferirlo
reduce 
carrito.reduce((s,i)=>s+i.cantidad*precio(i),0)
 Expresa "acumular un valor" en una sola línea; ideal para sumas, promedios, agrupaciones
for / for...of 
let t=0; for(const i of carrito){ t+=... }
 Más explícito para quien recién aprende, o cuando la lógica del acumulador es compleja (varias condiciones, side-effects)
Antiejemplo: guardar el total en localStorage
// ❌ Guardar un total "congelado" obliga a recordar actualizarlo
// cada vez que cambia el carrito, y es fácil que quede desactualizado.

El total se calcula a partir del carrito y el catálogo cada vez que se necesita mostrar; nunca se guarda como un valor aparte que pueda quedar desincronizado.

Validar y "confirmar" el pedido

app.js
document.getElementById('formCheckout').addEventListener('submit', (evento) => {
  evento.preventDefault();                    // evita que el formulario recargue la página

  const formulario = evento.target;
  if (!formulario.checkValidity()) {           // usa la validación nativa de HTML5
    formulario.classList.add('was-validated'); // Bootstrap resalta los campos inválidos
    return;
  }

  if (obtenerCarrito().length === 0) return;

  // Aquí, en un proyecto real, se enviaría el pedido a un servidor:
  // await fetch('/api/pedidos', { method: 'POST', body: JSON.stringify({...}) })

  localStorage.removeItem(CLAVE_CARRITO);      // se vacía el carrito
  document.dispatchEvent(new CustomEvent('carrito:actualizado', { detail: [] }));

  bootstrap.Modal.getInstance(document.getElementById('modalCheckout')).hide();
  new bootstrap.Modal(document.getElementById('modalConfirmacion')).show();

  formulario.reset();
  formulario.classList.remove('was-validated');
});
Por qué validar con checkValidity() antes de "enviar"
HTML5 ya sabe validar campos requeridos, formato de email, etc. usando atributos como required y type="email". Reutilizar esa validación nativa (en vez de escribir expresiones regulares a mano) reduce código y errores; Bootstrap solo se encarga de que se vea bien.
Por qué bootstrap.Modal.getInstance(...)
Cuando un modal se abre con data-bs-toggle="modal", Bootstrap crea automáticamente una instancia de JavaScript asociada a ese elemento. getInstance recupera esa instancia ya existente (en vez de crear una nueva) para poder llamar .hide() sobre ella y cerrar el modal de checkout justo antes de mostrar el de confirmación.
Antiejemplo: confiar en el precio que envía el navegador
// ❌ En un checkout real conectado a un servidor, nunca se debe
// confiar en el total calculado en el navegador: cualquiera puede
// abrir la consola y cambiarlo antes de enviarlo.
fetch('/api/pedidos', {
  method: 'POST',
  body: JSON.stringify({ total: totalMostradoEnPantalla }) // ❌ inseguro
});
El servidor debe recalcular el total a partir de los id y cantidades recibidas, usando sus propios precios — el front-end solo calcula para mostrarle el total al usuario.
Checkpoint del paso 09

12 CIERRE

Siguientes pasos

Este carrito con localStorage es suficiente para portafolios, prototipos y aprendizaje. Para un e-commerce real, la evolución típica es:

  • Backend + base de datos: mover el catálogo y el carrito a un servidor (Node/Express, Django, Laravel…) para compartir inventario real entre usuarios.
  • Autenticación: para que el carrito se asocie a una cuenta y no solo a un navegador.
  • Pasarela de pago (Stripe, MercadoPago, PayU…): el cobro nunca debe depender solo del front-end.
  • Framework de UI (React/Vue/Svelte) si la interfaz crece mucho: facilita mantener sincronizados muchos componentes que dependen del mismo estado.
El concepto que no cambia
Aunque cambie dónde vive el carrito (localStorage → servidor), la idea central se mantiene: guardar una lista mínima de {id, cantidad} y cruzarla con los datos del catálogo cada vez que hay que mostrarla o cobrarla.
