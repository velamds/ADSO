Conceptos fundamentales del Modelo ER

Antes de transformar, necesitamos dominar el vocabulario. El modelo Entidad-Relación (ER) es un mapa conceptual: describe el mundo en términos de cosas, sus características y cómo se relacionan entre sí. La base de datos relacional es la implementación física de ese mapa.

Mundo ER (conceptual)

  • Entidad — cosa del mundo real (Cliente, Producto)
  • Atributo — propiedad de la entidad (nombre, precio)
  • Atributo identificador — identifica unívocamente (cédula, SKU)
  • Relación — vínculo entre entidades (compra, pertenece a)
  • Cardinalidad — cuántas instancias participan (1:1, 1:N, M:N)
  • Participación — obligatoria (total) o no (parcial)

Mundo SQL (físico)

  • Tabla — agrupa registros del mismo tipo
  • Columna — propiedad con tipo de dato
  • Primary Key (PK) — identifica cada fila
  • Foreign Key (FK) — referencia a otra tabla
  • Tabla pivote — implementa M:N
  • Constraint — NOT NULL, UNIQUE, CHECK
PK — Clave Primaria FK — Clave Foránea UK — Clave Única NN — Not Null
Regla de oro: El modelo ER describe el QUÉ. El esquema relacional describe el CÓMO. La transformación es mecánica y se puede aplicar con reglas claras.
PASO 1

Cada entidad se convierte en una tabla

La regla más directa de la transformación: una entidad en el modelo ER = una tabla en la base de datos. El nombre de la entidad se convierte en el nombre de la tabla (generalmente en plural y en minúsculas).

Tipos de atributos especiales

A

Atributo compuesto

Dirección (calle, ciudad, estado, CP) → Se descompone en columnas individuales: dir_calle, dir_ciudad, dir_estado, dir_codigo_postal. O se crea una tabla separada direcciones.

B

Atributo multivaluado

Teléfonos (un cliente puede tener varios) → Se crea una tabla separada telefonos_cliente(id, cliente_id FK, numero, tipo). Nunca uses columnas como tel_1, tel_2, tel_3.

C

Atributo derivado

Edad (derivada de fecha_nacimiento) → Generalmente no se almacena; se calcula en la consulta. Excepción: si la consulta es muy frecuente, se puede usar una columna calculada o vista.

PASO 3

Identificar y asignar claves primarias (PK)

El atributo identificador del modelo ER se convierte en la Primary Key de la tabla. Hay dos estrategias principales:

Clave natural (del negocio)

Usa un atributo que ya existe y es único en el dominio.

-- Ejemplos de claves naturales
cedula       VARCHAR(20)
rfc          VARCHAR(13)
codigo_iso   CHAR(3)   -- países
isbn         VARCHAR(13) -- libros
email        VARCHAR(200)

⚠ Problema: pueden cambiar, son largos como FK.

Clave surrogada (artificial)

Se genera automáticamente, sin significado de negocio.

-- Entero autoincremental
id SERIAL PRIMARY KEY

-- UUID (distribuido)
id UUID PRIMARY KEY
   DEFAULT gen_random_uuid()

✓ Estable, compacto, ideal para FK.

Recomendación práctica: Usa clave surrogada (id SERIAL) como PK. Si el atributo natural debe ser único, agrégale UNIQUE NOT NULL como restricción adicional. Esto te da lo mejor de ambos mundos.

Clave primaria compuesta

Cuando ningún atributo solo identifica a la entidad, se combina más de uno. Común en tablas pivote de relaciones M:N.

CREATE TABLE pedido_productos (
  pedido_id   INT  NOT NULL,
  producto_id INT  NOT NULL,
  cantidad    INT  NOT NULL,
  precio_unit NUMERIC(10,2) NOT NULL,

  PRIMARY KEY (pedido_id, producto_id),
  FOREIGN KEY (pedido_id)   REFERENCES pedidos(id),
  FOREIGN KEY (producto_id) REFERENCES productos(id)
);
PASO 4

Relación Uno a Muchos (1:N) → clave foránea

Es la relación más común. Un registro del lado "1" se asocia con muchos registros del lado "N". La regla es simple: la clave foránea va en la tabla del lado N.

Regla 1:N: La PK del lado "1" (categoria.id) se copia como FK en la tabla del lado "N" (producto.categoria_id). 
CREATE TABLE categorias (
  id     SERIAL       PRIMARY KEY,
  nombre VARCHAR(100) NOT NULL
);

CREATE TABLE productos (
  id           SERIAL        PRIMARY KEY,
  nombre       VARCHAR(200)  NOT NULL,
  precio       NUMERIC(10,2) NOT NULL CHECK (precio >= 0),
  stock        INT           NOT NULL DEFAULT 0,
  categoria_id INT           NOT NULL,

  CONSTRAINT fk_producto_categoria
    FOREIGN KEY (categoria_id)
    REFERENCES categorias(id)
    ON DELETE RESTRICT
    ON UPDATE CASCADE
);

Comportamiento ON DELETE / ON UPDATE

Opciones de integridad referencial
OpciónQué haceCuándo usar
RESTRICT Bloquea el borrado del padre si tiene hijos Cuando los hijos son críticos (no se deben perder)
CASCADE Borra/actualiza los hijos automáticamente Relaciones donde los hijos no existen sin el padre
SET NULL La FK del hijo se pone en NULL La relación es opcional (padre puede desaparecer)
SET DEFAULT La FK toma su valor DEFAULT Hay un padre "genérico" o de fallback
NO ACTION Similar a RESTRICT, verificación diferida Transacciones complejas con verificación al final
PASO 5

Relación Muchos a Muchos (M:N) → tabla intermedia

Una relación M:N no se puede representar directamente con una FK. La solución es crear una tabla intermedia (pivote) que contiene las PKs de ambas tablas como FKs. Esta tabla representa cada par de asociación.

CREATE TABLE pedidos (
  id          SERIAL        PRIMARY KEY,
  cliente_id  INT           NOT NULL REFERENCES clientes(id),
  fecha       TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
  estado      VARCHAR(30)   NOT NULL DEFAULT 'pendiente',
  total       NUMERIC(12,2) NOT NULL DEFAULT 0
);

-- Tabla pivote: un pedido contiene muchos productos,
-- un producto puede estar en muchos pedidos
CREATE TABLE pedido_productos (
  pedido_id   INT           NOT NULL REFERENCES pedidos(id)   ON DELETE CASCADE,
  producto_id INT           NOT NULL REFERENCES productos(id)  ON DELETE RESTRICT,
  cantidad    INT           NOT NULL CHECK (cantidad > 0),
  precio_unit NUMERIC(10,2) NOT NULL,   -- precio al momento de compra

  PRIMARY KEY (pedido_id, producto_id)
);
¿Por qué guardar precio_unit en la pivote? El precio de un producto puede cambiar. Si guardas solo el FK al producto, perderás el precio histórico del pedido. Siempre almacena los datos que pueden variar con el tiempo en la relación, no solo en la entidad.
PASO 6

Relación Uno a Uno (1:1)

En una relación 1:1, cada registro de A se asocia con máximo un registro de B y viceversa. Tienes tres opciones de implementación:

Opción A: Fusionar en una sola tabla

La más simple. Si las dos entidades siempre aparecen juntas y tienen ciclo de vida idéntico, combínalas.

-- Usuario y Perfil → una sola tabla si son inseparables
CREATE TABLE usuarios (
  id           SERIAL       PRIMARY KEY,
  email        VARCHAR(200) UNIQUE NOT NULL,
  password_hash TEXT        NOT NULL,
  -- atributos del "perfil" fusionados:
  nombre       VARCHAR(100),
  avatar_url   TEXT,
  bio          TEXT
);

Opción B: FK en la tabla opcional (más común)

Una entidad es obligatoria (siempre existe) y la otra es opcional (puede o no existir). La FK va en la tabla opcional.

CREATE TABLE empleados (
  id        SERIAL       PRIMARY KEY,
  nombre    VARCHAR(100) NOT NULL,
  cargo     VARCHAR(100) NOT NULL
);

-- No todos los empleados tienen auto de empresa,
-- pero cada auto pertenece a un único empleado.
CREATE TABLE autos_empresa (
  id          SERIAL       PRIMARY KEY,
  placa       VARCHAR(10)  UNIQUE NOT NULL,
  modelo      VARCHAR(100) NOT NULL,
  empleado_id INT          UNIQUE REFERENCES empleados(id) ON DELETE SET NULL
  -- UNIQUE garantiza que ningún empleado tenga 2 autos
);

Opción C: Tabla separada con FK que es también PK

Las entidades son independientes pero se relacionan. La segunda tabla usa la misma PK que la primera.

CREATE TABLE usuarios (
  id    SERIAL       PRIMARY KEY,
  email VARCHAR(200) UNIQUE NOT NULL
);

-- La configuración solo existe si el usuario la personaliza
CREATE TABLE configuracion_usuario (
  usuario_id   INT         PRIMARY KEY REFERENCES usuarios(id) ON DELETE CASCADE,
  tema         VARCHAR(20) DEFAULT 'claro',
  idioma       CHAR(5)     DEFAULT 'es-MX',
  notificaciones BOOLEAN  DEFAULT TRUE
);
¿Cuándo separar en 1:1? Cuando la entidad opcional tiene muchos atributos, cuando se accede por separado frecuentemente, o cuando quieres mantener una tabla "core" liviana.
PASO 7

Atributos propios de una relación

En el modelo ER, las relaciones pueden tener sus propios atributos. Por ejemplo, la relación "un empleado trabaja en un proyecto" tiene el atributo horas_semanales. Estos atributos no pertenecen a ninguna de las dos entidades: pertenecen a la relación.

Caso real: Empleados y Proyectos

Un empleado puede trabajar en varios proyectos. Un proyecto tiene varios empleados. La relación "trabaja_en" tiene sus propios datos: rol en el proyecto, fecha de inicio, horas por semana.

Los atributos de la relación van directamente en la tabla intermedia / pivote:

CREATE TABLE empleados (
  id     SERIAL        PRIMARY KEY,
  nombre VARCHAR(100)  NOT NULL,
  cargo  VARCHAR(100)
);

CREATE TABLE proyectos (
  id     SERIAL       PRIMARY KEY,
  nombre VARCHAR(200) NOT NULL,
  fecha_inicio DATE
);

-- Tabla de la relación M:N con atributos propios
CREATE TABLE asignaciones (
  empleado_id    INT          NOT NULL REFERENCES empleados(id),
  proyecto_id    INT          NOT NULL REFERENCES proyectos(id),
  rol_en_proyecto VARCHAR(100) NOT NULL,   -- atributo de la relación
  horas_semanales DECIMAL(4,1) CHECK (horas_semanales BETWEEN 1 AND 60),
  fecha_inicio    DATE         NOT NULL DEFAULT CURRENT_DATE,
  fecha_fin       DATE,

  PRIMARY KEY (empleado_id, proyecto_id)
);
PASO 8

Herencia / Entidades especializadas

En el modelo ER extendido (EER) existe la generalización/especialización: una entidad "padre" tiene subtipos. Por ejemplo, Persona se especializa en Empleado y Cliente. Hay tres estrategias de mapeo:

Estrategia 1: Tabla única (Single Table Inheritance)

Una sola tabla con todos los atributos. Una columna tipo discrimina el subtipo.

CREATE TABLE personas (
  id           SERIAL      PRIMARY KEY,
  tipo         VARCHAR(20) NOT NULL CHECK (tipo IN ('empleado','cliente','proveedor')),
  nombre       VARCHAR(100) NOT NULL,
  email        VARCHAR(200) UNIQUE NOT NULL,
  -- columnas de empleado (NULL para clientes)
  numero_emp   VARCHAR(20),
  departamento VARCHAR(100),
  salario      NUMERIC(12,2),
  -- columnas de cliente (NULL para empleados)
  rfc          VARCHAR(13),
  credito_max  NUMERIC(12,2)
);
Ventaja: Consultas simples, una sola tabla. Desventaja: Muchos NULLs, no se pueden poner NOT NULL en columnas de subtipos.

Estrategia 2: Tabla por subtipo (Class Table Inheritance) — Recomendada

Una tabla padre con los atributos comunes. Cada subtipo tiene su propia tabla con los atributos específicos, usando la misma PK.

CREATE TABLE personas (
  id     SERIAL       PRIMARY KEY,
  nombre VARCHAR(100) NOT NULL,
  email  VARCHAR(200) UNIQUE NOT NULL
);

CREATE TABLE empleados (
  persona_id   INT          PRIMARY KEY REFERENCES personas(id) ON DELETE CASCADE,
  numero_emp   VARCHAR(20)  UNIQUE NOT NULL,
  departamento VARCHAR(100) NOT NULL,
  salario      NUMERIC(12,2) NOT NULL
);

CREATE TABLE clientes (
  persona_id  INT          PRIMARY KEY REFERENCES personas(id) ON DELETE CASCADE,
  rfc         VARCHAR(13)  UNIQUE,
  credito_max NUMERIC(12,2) DEFAULT 0
);
Ventaja: Sin NULLs espurios, restricciones correctas por subtipo. Desventaja: JOINs necesarios para obtener datos completos.

Estrategia 3: Tabla por subtipo completo (Concrete Table Inheritance)

Cada subtipo tiene una tabla completamente independiente con todos sus atributos (incluyendo los heredados). No hay tabla padre.

Desventaja importante: Los atributos comunes se duplican. Si cambias el atributo "nombre" en la entidad padre, debes actualizar todas las tablas hijo. Úsala solo cuando los subtipos raramente se consultan juntos.
PASO 9

Caso Completo — Sistema de E-Commerce

Descripción del negocio

Una tienda en línea vende productos organizados en categorías. Los clientes crean cuentas, agregan productos a un carrito y generan pedidos. Cada pedido tiene una dirección de envío y puede contener varios productos con cantidades específicas. Los productos tienen un historial de precios. Los clientes pueden dejar reseñas.

Modelo ER (conceptual)

Esquema SQL completo resultante

-- ============================================
-- SISTEMA DE E-COMMERCE — Esquema Relacional
-- ============================================

-- 1. Catálogo
CREATE TABLE categorias (
  id          SERIAL       PRIMARY KEY,
  nombre      VARCHAR(100) UNIQUE NOT NULL,
  descripcion TEXT,
  activa      BOOLEAN      NOT NULL DEFAULT TRUE
);

CREATE TABLE productos (
  id           SERIAL         PRIMARY KEY,
  categoria_id INT            NOT NULL REFERENCES categorias(id),
  nombre       VARCHAR(200)   NOT NULL,
  sku          VARCHAR(50)    UNIQUE NOT NULL,
  descripcion  TEXT,
  precio       NUMERIC(10,2)  NOT NULL CHECK (precio >= 0),
  stock        INT            NOT NULL DEFAULT 0 CHECK (stock >= 0),
  peso_kg      NUMERIC(8,3),
  activo       BOOLEAN        NOT NULL DEFAULT TRUE,
  creado_en    TIMESTAMPTZ    NOT NULL DEFAULT NOW()
);

CREATE TABLE imagenes_producto (
  id          SERIAL      PRIMARY KEY,
  producto_id INT         NOT NULL REFERENCES productos(id) ON DELETE CASCADE,
  url         TEXT        NOT NULL,
  alt_text    VARCHAR(200),
  orden       SMALLINT    NOT NULL DEFAULT 0
);

-- 2. Clientes y Direcciones
CREATE TABLE clientes (
  id            SERIAL       PRIMARY KEY,
  nombre        VARCHAR(100) NOT NULL,
  apellido      VARCHAR(100) NOT NULL,
  email         VARCHAR(200) UNIQUE NOT NULL,
  password_hash TEXT         NOT NULL,
  telefono      VARCHAR(20),
  activo        BOOLEAN      NOT NULL DEFAULT TRUE,
  creado_en     TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

CREATE TABLE direcciones (
  id          SERIAL       PRIMARY KEY,
  cliente_id  INT          NOT NULL REFERENCES clientes(id) ON DELETE CASCADE,
  alias       VARCHAR(50)  NOT NULL DEFAULT 'Casa',
  calle       VARCHAR(200) NOT NULL,
  ciudad      VARCHAR(100) NOT NULL,
  estado      VARCHAR(100) NOT NULL,
  codigo_postal VARCHAR(10) NOT NULL,
  pais        CHAR(2)      NOT NULL DEFAULT 'MX',
  es_principal BOOLEAN     NOT NULL DEFAULT FALSE
);

-- 3. Pedidos
CREATE TABLE pedidos (
  id             SERIAL       PRIMARY KEY,
  cliente_id     INT          NOT NULL REFERENCES clientes(id),
  direccion_id   INT          NOT NULL REFERENCES direcciones(id),
  estado         VARCHAR(30)  NOT NULL DEFAULT 'pendiente'
                               CHECK (estado IN ('pendiente','pagado','enviado','entregado','cancelado')),
  total          NUMERIC(12,2) NOT NULL CHECK (total >= 0),
  notas          TEXT,
  creado_en      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  actualizado_en TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

-- Tabla pivote M:N con atributos propios
CREATE TABLE pedido_productos (
  pedido_id   INT           NOT NULL REFERENCES pedidos(id)   ON DELETE CASCADE,
  producto_id INT           NOT NULL REFERENCES productos(id)  ON DELETE RESTRICT,
  cantidad    INT           NOT NULL CHECK (cantidad > 0),
  precio_unit NUMERIC(10,2) NOT NULL,
  descuento   NUMERIC(5,2)  NOT NULL DEFAULT 0,

  PRIMARY KEY (pedido_id, producto_id)
);

-- 4. Reseñas (M:N entre cliente y producto, con atributos)
CREATE TABLE resenas (
  id          SERIAL      PRIMARY KEY,
  cliente_id  INT         NOT NULL REFERENCES clientes(id)  ON DELETE CASCADE,
  producto_id INT         NOT NULL REFERENCES productos(id) ON DELETE CASCADE,
  calificacion SMALLINT   NOT NULL CHECK (calificacion BETWEEN 1 AND 5),
  titulo      VARCHAR(200),
  cuerpo      TEXT,
  verificada  BOOLEAN     NOT NULL DEFAULT FALSE,
  creado_en   TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  UNIQUE (cliente_id, producto_id)  -- un cliente, una reseña por producto
);

-- 5. Índices para consultas frecuentes
CREATE INDEX idx_productos_categoria  ON productos(categoria_id);
CREATE INDEX idx_pedidos_cliente       ON pedidos(cliente_id);
CREATE INDEX idx_pedidos_estado        ON pedidos(estado);
CREATE INDEX idx_direcciones_cliente   ON direcciones(cliente_id);
CREATE INDEX idx_resenas_producto      ON resenas(producto_id);

Datos de ejemplo y consultas

-- Insertar datos de prueba
INSERT INTO categorias (nombre) VALUES ('Electrónica'), ('Ropa'), ('Libros');

INSERT INTO productos (categoria_id, nombre, sku, precio, stock)
VALUES
  (1, 'Laptop Pro 15"',  'TECH-001', 22999.00, 15),
  (1, 'Mouse Inalámbrico', 'TECH-002',  349.00, 80),
  (3, 'Clean Code',       'BOOK-001',  680.00, 30);

-- Consulta: pedidos con sus productos y total
SELECT
  p.id          AS pedido,
  c.nombre || ' ' || c.apellido AS cliente,
  pr.nombre     AS producto,
  pp.cantidad,
  pp.precio_unit,
  (pp.cantidad * pp.precio_unit) AS subtotal,
  p.estado
FROM        pedidos          p
JOIN        clientes         c  ON c.id  = p.cliente_id
JOIN        pedido_productos pp ON pp.pedido_id   = p.id
JOIN        productos        pr ON pr.id = pp.producto_id
ORDER BY    p.id, pr.nombre;

-- Consulta: promedio de calificaciones por producto
SELECT
  pr.nombre,
  ROUND(AVG(r.calificacion), 1) AS promedio,
  COUNT(r.id)                   AS total_resenas
FROM      productos pr
LEFT JOIN resenas   r ON r.producto_id = pr.id
GROUP BY  pr.id, pr.nombre
ORDER BY  promedio DESC NULLS LAST;

RESUMEN

Reglas de transformación de un vistazo

1

Entidad → Tabla

Una tabla por entidad. Nombre en minúsculas y snake_case.

2

Atributo → Columna (con tipo de dato y restricción)

Compuesto → múltiples columnas o tabla separada. Multivaluado → tabla separada. Derivado → calcular en consulta.

3

Identificador → PRIMARY KEY

Preferir surrogada (SERIAL) + restricción UNIQUE en la clave natural.

4

Relación 1:N → FOREIGN KEY en el lado N

La PK del "1" se copia como FK en la tabla del "N".

5

Relación M:N → Tabla intermedia (pivote)

Contiene las FKs de ambas tablas como PK compuesta. Los atributos de la relación van aquí.

6

Relación 1:1 → FK con UNIQUE, fusión, o PK compartida

Depende de si la relación es obligatoria/opcional y de los patrones de acceso.

7

Atributos de relación → columnas en la pivote

Si la relación M:N tiene sus propios atributos, van en la tabla intermedia.

8

Herencia → una tabla, tabla por subtipo, o tabla por concreto

Preferir "tabla por subtipo" para mantener restricciones y evitar NULLs.
