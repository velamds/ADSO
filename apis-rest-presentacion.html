01 — Fundamentos

APIs REST

Cómo el estilo arquitectónico que hoy mueve la web —definido por Roy Fielding en el año 2000— sigue siendo la base de casi cualquier API moderna.

Conceptos originales · comparativas prácticas · JSON Server · consumo con React

02 — El concepto

REST no es un protocolo, es un estilo arquitectónico

Fielding definió seis restricciones que, cumplidas juntas, hacen que un sistema sea "RESTful". La mayoría de las "APIs REST" del mundo real solo cumplen algunas.

01

Cliente–Servidor

Separación de responsabilidades: la interfaz de usuario vive aparte del almacenamiento de datos.

02

Sin estado (stateless)

Cada petición contiene toda la información necesaria; el servidor no guarda contexto entre llamadas.

03

Cacheable

Las respuestas se marcan como cacheables o no, para evitar peticiones innecesarias.

04

Interfaz uniforme

Recursos identificados por URI, manipulados con representaciones (normalmente JSON).

05

Sistema por capas

El cliente no sabe si habla con el servidor final o con un intermediario (proxy, gateway).

06

Código bajo demanda

Restricción opcional: el servidor puede enviar lógica ejecutable al cliente.

03 — Arquitectura

Cliente, servidor y statelessness en la práctica

Cada flecha de ida es una petición completa (URL + método + headers + body). El servidor no recuerda la anterior: por eso escala horizontalmente sin problema.

06 — Respuestas

Códigos de estado esenciales

200 OK
 Petición exitosa
201 Created
 Recurso creado (típico tras un POST)
204 No Content
 Éxito sin cuerpo de respuesta (típico tras un DELETE)
400 Bad Request
 La petición del cliente es inválida
404 Not Found
 El recurso solicitado no existe
500 Server Error
 Fallo en el servidor
07 — Prototipado rápido

JSON Server: una API REST a partir de un archivo JSON

Ideal para simular un backend real mientras se desarrolla el frontend, sin escribir ni una línea de servidor.

1. db.json

{
  "usuarios": [
    { "id": 1, "nombre": "Ana" },
    { "id": 2, "nombre": "Luis" }
  ]
}

2. Levantar el servidor

npm install -g json-server

json-server --watch db.json --port 3001

Genera automáticamente GET, POST, PUT, PATCH y DELETE sobre http://localhost:3001/usuarios

08 — Consumo desde el cliente

Consumir la API con React y Fetch

Leer usuarios (GET)

useEffect(() => {
  fetch("http://localhost:3001/usuarios")
    .then(res => res.json())
    .then(data => setUsuarios(data))
    .catch(err => console.error(err));
}, []);

Crear usuario (POST)

fetch("http://localhost:3001/usuarios", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ nombre: "Carla" })
})
  .then(res => res.json())
  .then(nuevo => setUsuarios([...usuarios, nuevo]));

JSON Server simula el backend completo; React solo necesita fetch apuntando a esa URL como si fuera producción.

09 — Consumo desde el cliente

Actualizar y eliminar: PUT, PATCH y DELETE

Reemplazar usuario (PUT)

fetch(`http://localhost:3001/usuarios/${id}`, {
  method: "PUT",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ id, nombre: "Carla Ruiz" })
})
  .then(res => res.json())
  .then(actualizado =>
    setUsuarios(usuarios.map(u =>
      u.id === id ? actualizado : u
    ))
  );

Modificar parcial (PATCH)

fetch(`http://localhost:3001/usuarios/${id}`, {
  method: "PATCH",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ nombre: "Carla R." })
})
  .then(res => res.json())
  .then(actualizado =>
    setUsuarios(usuarios.map(u =>
      u.id === id ? actualizado : u
    ))
  );

Eliminar usuario (DELETE)

fetch(`http://localhost:3001/usuarios/${id}`, {
  method: "DELETE"
})
  .then(() =>
    setUsuarios(usuarios.filter(u => u.id !== id))
  );

PUT reemplaza el recurso completo; PATCH solo los campos enviados; DELETE no suele devolver cuerpo (204 No Content), por eso aquí no se hace res.json().
